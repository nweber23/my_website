Testing Raft with a fake clock: deterministic chaos in Go

2026-11-02 · raftlab

Raft is easy to read and hard to trust. The paper is a few pages long, and the bugs live in the interleavings: a message that arrives after a leader change, a timer that fires just before it is stopped, a crash halfway through a write. I wrote raftlab, a Raft implementation in Go with a replicated key-value store and a browser visualizer, and the part I would keep if I had to throw the rest away is how it is tested.

Four seams and no clock

The core, raft.Node, implements Figure 2 of the Raft paper and nothing else. It has no goroutines and no knowledge of sockets or wall-clock time. Everything it touches goes through one of four interfaces:

Transport     send RPCs to peers
Clock         election and heartbeat timers
Storage       durable term, vote, log, snapshot
StateMachine  apply committed commands

Each has a real implementation and a test one. Transport is HTTP in a real cluster, an in-process network with fault injection in the visualizer, and a manual in-memory one in unit tests. Clock is the system clock or a fake one. Storage is a checksummed write-ahead log. StateMachine is the key-value store, or a recorder in tests.

Because time and I/O are injected, a whole five-node cluster can run on the fake clock inside a single-threaded test. Nothing sleeps. The test advances virtual time in 10 ms steps and the fake network delivers messages when their virtual delay has passed. A run is then a pure function of its random seed: same seed, same elections, same failures.

The chaos test

The chaos test runs five nodes for 40 virtual seconds. It randomly crashes and restarts nodes, partitions the network, and injects loss, duplication and delay, while four clients set, delete and read two shared keys, half of the reads through the log and half through ReadIndex. After every 10 ms step it checks two safety properties: election safety (never two leaders in the same term) and committed-prefix agreement (no two nodes disagree about an entry they have both committed).

At the end it heals the cluster, checks that the replicas converge, and hands the complete recorded history to a linearizability checker (more on that below). A failure prints its seed, and replaying it is one command:

CHAOS_SEED=17 go test -run Chaos ./internal/kv
make test-chaos    # 100 seeds

That replay is what makes the test useful. A distributed test that fails once in a hundred runs and never again teaches you nothing. A failing seed can be rerun, stepped through and kept as a regression test.

A checker that gives the test teeth

The first version only checked that a read returned the last acknowledged write, which is weaker than linearizability. I replaced it with a real checker, internal/linz, an implementation of the Wing–Gong/Lowe search with memoization, written for this repo. Every operation is recorded with its call and return time, keys are independent so the history is split per key, and each part must be explainable as one sequential order that respects real time. A seed produces 1,000 to 1,700 operations, and all of them have to fit.

A checker is only worth something if it fails when it should, so I injected two bugs and restored the code afterwards:

  • ReadIndex serving a read without confirming leadership: caught by seeds 25 and 39 of the first 40, with the report that a read of an old value cannot be placed.
  • Request deduplication removed, so a retried delete runs twice: caught by seed 35, naming the delete that cannot be placed.

The first bug initially slipped through all 40 seeds. With PreVote and CheckQuorum on, a deposed leader steps down before a new one can commit anything, so the window for a stale read barely exists. The chaos test now runs odd seeds in the classic protocol, where a deposed leader lingers. A checker can only flag what the system does.

Two tests that proved nothing

Mutation testing caught my own tests twice. My first joint-consensus test still passed after I deleted the old-majority requirement from the quorum function, because in that setup the old side could not have committed anyway. I rebuilt the scenario so that only that rule stops the commit. My first packet-loss test for pipelining passed with the stall recovery disabled, because random loss triggers leader changes that reset replication state and hide the bug. The replacement loses a whole burst for 60 ms with nothing new proposed, so only the stall check can recover.

What a fake clock cannot find

The bug that stayed hidden longest was in the clock itself. A real clock can run a callback that fired just before Stop was called. In raftlab that means a stale election timer can still run, start a spurious election and depose a healthy leader. The fake clock cannot reproduce it, because the fake clock never runs a callback concurrently with a stop.

The fix is to replace timers instead of resetting them and to give each one a generation counter, so a callback from an old generation does nothing. A hand-driven clock covers it in tests. The lesson is the limit of the whole approach: deterministic simulation finds the interleavings you modelled, and the concurrency of the clock was not one of them.

Two bugs about late and repeated messages

Both come from the network delaying, reordering or duplicating messages, which is exactly what the fault injector does.

A delayed AppendEntries erased newer entries. An old request arriving late truncated the follower's log even though nothing in it conflicted. The log is now truncated only on a real conflict.

Reordered and duplicated replies moved nextIndex backwards. A stale reply made the leader forget how much of a follower's log it had already matched. Replies now carry MatchIndex, so a stale one cannot regress the leader's view of a follower.

A bug only Windows could find

I found this one while recording the demo, not in a test. Windows cannot rename over an open file, so the first time a node compacted its log it panicked. Compaction writes a new file, fsyncs it and renames it over the old one, so a crash leaves either the old file or the new one and never a mix. The write-ahead log now closes its handles before the rename and reopens them afterwards, and skips the directory fsync on Windows, where directories cannot be opened for sync. It is a reminder that the simulation checks the algorithm and not the operating system.

What the roadmap turned into

Everything this post once listed as future work is built and tested on the same fake clock: PreVote and CheckQuorum, membership changes by joint consensus, ReadIndex reads that skip the log, chunked snapshots, and pipelined replication. Pipelining is the one with a number: a burst of 1,000 proposals sent 2,012,480 entries on the wire before and 2,000 after, exactly one copy per follower, and applied everywhere in 120 ms instead of 670 ms. Server-issued client IDs with deterministic session expiry and mutual TLS between nodes came along too.

The latest round made membership changes work in the standalone raftnode binary, not just in the visualizer. Configuration entries carry server addresses and the HTTP transport can add peers at runtime. A new server joins with -join and first catches up as a non-voting learner, so a far-behind newcomer cannot stall commits. The leader also tells servers it removed that they are gone. The write-ahead log gained a versioned file header, and older files still open.

What is left is deliberate: leader leases as a cheaper alternative to ReadIndex. They trade correctness for an assumption about clock drift, and the reasoning is written down with the other trade-offs in the repository.
