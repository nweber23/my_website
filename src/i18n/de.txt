@@ qwjj7e
Die gesamte Aufgabe einer Shell ist Prozessorchestrierung – fork/exec, Pipe-Verkettung, Signalzustellung, Umleitungen. Dafür eine Bibliothek zu nehmen, hieße, eine Shell um eine Shell herum zu bauen. Der WebSocket-Hub von Transcendence: Kontrolle statt fertiger Socket-Schicht
@@ bbxgpu

Die interne Grenze: warum gRPC für Go ↔ C++
@@ 1h2inet
An der Grenze zwischen Go-Backend und C++-Engine gelten die umgekehrten Anforderungen. Kein Browser spricht sie direkt an, Lesbarkeit bringt also nichts, aber zwei Sprachen müssen sich jetzt Byte für Byte einig sein, wie eine Anfrage „diese Pokerhand auswerten“ aussieht – und genau diese Art Vertrag verrottet über ein von Hand gepflegtes, zwischen zwei Codebasen geteiltes JSON-Schema unbemerkt. Ein auf einer Seite umbenanntes Feld, ein int gegen ein float auf der anderen, ein optionales Feld, dessen Prüfung eine Seite vergisst: alles unsichtbar, bis eine Hand in Produktion falsch ausgewertet wird. <strong>gRPC</strong> und <code>.proto</code>-Dateien beheben das, indem das Schema zur einzigen Quelle der Wahrheit wird – <code>protoc</code> erzeugt zueinander passende Go- und C++-Stubs aus derselben Definition, sodass eine inkompatible Änderung an einer Nachrichtenform auf beiden Seiten der Grenze ein Kompilierfehler ist und keine Laufzeitüberraschung.
@@ 1yuvm14
Was gRPC über Typsicherheit hinaus bringt
@@ 1ljjv60
Drei konkrete Dinge für genau diese Grenze. Erstens ist die binäre Protobuf-Kodierung über HTTP/2 pro Aufruf spürbar billiger als JSON über HTTP/1.1, wenn das Backend für jede Aktion an jedem Tisch eine Handbewertung oder Einsatzabrechnung anfordert – ein Overhead, der bei ein paar Seitenaufrufen irrelevant ist, sich über gleichzeitige Tische aber summiert. Zweitens bedeutet HTTP/2-Multiplexing, dass viele gleichzeitige Aufrufe vom Go-Backend zur C++-Engine sich eine Verbindung ohne Head-of-Line-Blocking teilen, was zählt, sobald mehrere Tische im selben Tick Hände auswerten. Drittens dokumentiert sich eine <code>.proto</code>-Service-Definition selbst – der Vertrag steht in einer Datei, die zugleich der Code ist, statt auf einer Wiki-Seite, die vom tatsächlichen Verhalten der Endpunkte abdriftet.
@@ 1rlrjlm
Keines der Protokolle ist abstrakt „besser“ – REST hat am Browser-Rand aus denselben Gründen gewonnen, aus denen gRPC an der internen Grenze gewonnen hat: das Protokoll danach wählen, wer es lesen muss und wie oft es läuft. Eine öffentliche API, die externe Entwickler oder ein Browser nutzen, sollte auf Debugbarkeit und Verbreitung optimiert sein; eine private, hochfrequente, sprachübergreifende Grenze auf einen Vertrag, den der Compiler durchsetzt. Es ist dasselbe Denken in Protokollgrenzen wie hinter dem Topic-Fan-out des WebSocket-Hubs und dahinter, <a>Prozessgrenzen</a> bewusst zu gestalten, statt sie zu überspielen.

@@ z9p3x1
Die Engine läuft als gRPC-Server: Ein bidirektionaler <code>Play</code>-Stream ist ein Spiel. Der Client sendet <code>Reset(seed)</code> und dann Platzierungen, und jede Anfrage liefert den Zustand, die Belohnung und die Liste der gültigen Platzierungen zurück. Eine Python-Gymnasium-Umgebung spricht mit ihr, und vektorisierte Umgebungen lassen mehrere Spiele parallel laufen. Die Aktion ist eine einzelne Ganzzahl, <code>rot * 12 + (x + 2)</code>, mit einer Aktionsmaske für die gültigen. Auf meinem Rechner erreichten 4 Umgebungen etwa 5.200 Schritte pro Sekunde und 8 etwa 7.100, wobei ein Schritt eine Steinplatzierung ist.

Der Agent
@@ 1jags2k
Das Netz gibt keinen Wert pro Aktion aus. Es bewertet das <strong>Spielfeld nach einer Platzierung</strong> (den Afterstate) anhand derselben vier Merkmale wie die Heuristik, und der Agent spielt die Platzierung mit der höchsten Bewertung. Das Trainingsziel ist das übliche DQN-Ziel: die Belohnung plus der abgezinste beste Wert unter den Platzierungen des nächsten Steins, aus einem langsam aktualisierten Zielnetz.
@@ 1c7kz31
Das Netz ist ein kleines MLP (4-64-64-1). Der Rest ist Standard: ein Replay-Puffer mit 50k, ein hartes Ziel-Update alle 1.000 Schritte, Adam mit 1e-3, Batch 128, Gamma 0,99 und Epsilon, das über 50.000 von 100.000 Schritten von 1 auf 0,01 fällt. Belohnungen sind der Zeilenlösch-Score geteilt durch 100. Trainingspartien nutzen Seeds ab 1.000.000, die Validierung (10 greedy Partien alle 10.000 Schritte) nutzt 5001–5010, um den besten Checkpoint zu wählen, und die finalen Zahlen nutzen die Baseline-Seeds 1–100, auf denen der Agent nie trainiert hat.

Bevor ich das Projekt für fertig erklärte, habe ich <code>govulncheck</code> darauf laufen lassen. Es fand etwa zwei Dutzend Schwachstellen in der Go-Standardbibliothek, alle weil die Toolchain auf meinem Rechner Go 1.25.4 war, dazu einige in <code>golang.org/x/net</code>, das gRPC mitbringt. Der Scan sagt, der Code erreiche einige davon über gRPC und Ebitengine, obwohl der Server nur auf der Loopback-Adresse lauscht, und sie ließen sich leicht beseitigen. Die Lösung war, <code>go.mod</code> auf die neuere Toolchain zu heben (Go 1.27.2, die der <code>go</code>-Befehl selbst herunterlädt) und <code>x/net</code> samt Nachbarn zu aktualisieren. Das neuere <code>x/net</code> braucht Go 1.26, daher stieg die Mindestversion von Go im README von 1.25 auf 1.26. <code>govulncheck</code> meldet jetzt nichts mehr und die Tests bestehen. <code>pip-audit</code> auf der Python-Seite war die ganze Zeit sauber.
